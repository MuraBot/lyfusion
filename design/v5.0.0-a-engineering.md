> 状态:评审后第 2 版,2026-11-06。
> 第 1 版经 4 位评审,汇总见 `v5-review-synthesis.md`;评审时的版本(匿名)见 `design-review/design.md`。
> Lily 按汇总的推荐定了 7 个问题,并补充:续用的会话要由插件优雅地记住。
> 流程图(只画机制):`v5.0.0-a-flow.svg`;架构图(含实现):`v5.0.0-a-architecture.svg`。
> 本文是 v5 的设计方案和技术方案。它取代 v4 的"技能 + 派工脚本"形态,把 lyfusion 做成一个 Claude Code 插件。

## 1. 背景

### 1.1 lyfusion 是什么
lyfusion 是一种双代理编码协作方式:
- **lead**:一个前沿模型(Claude,在用户自己开着的 Claude Code 会话里),负责计划、决定、审查
- **助手(sidekick)**:一个更便宜、偏工程的代码模型(Codex CLI,例如 `gpt-6-luna`),负责实现、写测试、跑检查

目标是在长任务里,让结果的质量对齐"前沿模型单独做",同时只在需要判断的地方使用前沿模型。

### 1.2 v4 的形态和成绩
- 形态:一份给 lead 读的说明(约 90 行)、一份给助手读的说明(约 70 行)、一个 PowerShell 派工脚本(676 行,20 个参数)、一个台账程序(349 行)
- 流程:助手先只读探索 → lead 写计划 → 一条命令派工 → 脚本监工、跑测试和 lint、打交接包 → lead 审查 → 修改请求 → 验收提交
- 在一个真实的游戏模组项目里,两个里程碑交付质量不错、花费很少
- 在一个本地基准(9 道题)上,lead 的调用次数和前沿模型单独做持平。原因是短题里固定流程本身就要约 15 次调用

### 1.3 v4 暴露的问题
来自对那个游戏模组项目两个里程碑全部通信记录的诊断:
1. **长任务里 lead 对设计的把控会丢。** 用户在另一个商业双代理产品里也观察到同样的现象:短任务里助手能很好地执行前沿模型的审美,长任务里整体设计把控不如前沿模型单独做
2. **助手的问题没人回答。** 一个关于分支的问题在 3 次报告里出现,都没有得到回答,因为问题只在运行结束时出现
3. **助手上下文没有边界。** 一个 Codex 会话从第 2 个任务用到第 12 个任务,累计输入 1.52 亿 token,报告和修改请求的核对都受到干扰
4. **计划的完整度没有标准。** 有一次成功标准自相矛盾,助手为了通过把前一个任务的数值测试改弱了
5. **规则靠文字提醒。** 例如"前端由 lead 做""不要关证书检查",助手关了 3 次证书检查且没有报告;lead 也会漏步骤、传错会话编号
6. **分工只按"前端还是后端"。** 其他需要判断的工作没有覆盖
7. **续用要 lead 自己找。** 到了第 2 阶段,lead 还要自己去翻第 1 阶段的续用命令和会话编号

### 1.4 外部参考
Cognition 的 Devin Fusion 博客(2026-06)有几条结论和我们的问题直接相关:
- 两个**并行**的完整代理,各有自己的工具和**各自的缓存上下文**;比"顾问工具"(每次重新付上下文的钱)便宜
- 主代理默认只委派和监控,只做重大决定:计划、歧义的解释、最终审查;动作少,只读必要的东西
- 用轻量分类器在会话中途决定谁主导;在上下文压缩时切换模型,因为压缩本来就让缓存失效
- 五个案例里,"难的多文件 React 功能,考的是判断"用了双代理后分数从 54 掉到 27;"难但机械的集成"反而从 69 升到 81。结论:**判断本身就是交付物时,委派会适得其反**

## 2. 目标和非目标

### 2.1 目标
1. **质量是门槛**:长任务的结果不低于前沿模型单独做,尤其是设计和用户能感知的部分
2. **规则变程序**:流程上的约束由隔离、工具和检查保证,不靠文字提醒
3. **自然的入口**:打开 Fusion、选好助手的模型、推理强度和快速档,之后正常对话就是在用 lyfusion
4. **续用无感**:lead 从不接触会话编号。换任务、换阶段、换对话、上下文压缩之后,该接上的都自动接上
5. **并行而安全**:助手在自己的工作目录里写,lead 同时做自己的事,互不干扰
6. **可测量**:每个任务的 lead 和助手用量自动记录。用量是记录并报告的次要指标,不是优化目标
7. **可测试**:核心逻辑不依赖 Claude Code,能用假 Codex 自动测试,能拿去跑基准

### 2.2 非目标(5.0.0-a 不做)
- 多条工作线、多个助手同时工作(alpha 只有 1 条工作线)
- 助手提问的实时送达(`codex queue`)
- 台账面板和图表(放到 5.0.0-b)
- 会话中途在多个 Claude 模型之间切换
- 发布到插件市场(先从本地文件夹加载)
- 和立项、spec 类流程工具集成
- 在 Claude Code 之外驱动 Claude

## 3. 设计原则
1. **按"判断在哪"分工。** 每项工作标类型:判断、机械、验证、探索(见 4.2)
2. **计划要决定完整,不要步骤完整。** 每个任务写清三组边界:必须遵守、可以自己定、必须上报(见 4.5)
3. **品味先做成实物。** 判断类的工作,lead 先亲手做一个代表性样例,助手照着扩展
4. **意图有记录。** 决定带版本;能做成检查的决定就做成检查;助手自己做的决定要浮出来,由 lead 认可或驳回
5. **隔离代替拦截。** 助手在自己的工作目录和任务分支上写,lead 的目录它碰不到
6. **证据由程序产生,并绑定冻结的候选。** 检查由引擎去跑;验收只认某一个具体的候选提交
7. **交接是数据。** 任务单、报告、审查意见都有固定结构,由程序校验
8. **信号少而准,决定由 lead 做。** 用确定的规则代替分类器
9. **lead 读必要的东西,读多少由数据调。** alpha 默认给第 2 层,并记录问题是在哪一层发现的
10. **状态只有一个写入口。** 流程状态只由引擎写进事件库;代码归 git;原始日志归 `runs/`
11. **小事零仪式。** lead 可以直接做,不必走流程
12. **用成熟、无聊的技术。** Python 标准库、sqlite3、git,不引入服务端

## 4. 核心概念

### 4.1 任务、工作项、候选
- **任务**:一次交付,例如"让月结在补传后保持一致"。有目标、三组边界、验收检查、引用的决定
- **工作项**:任务里的一块工作,有类型、负责人、文件范围、对应的验收检查
- **候选**:助手一次运行结束后,引擎在任务分支上做的一个提交,编号如 `T3.c2`。检查、审查、验收都绑定某一个候选
- **两种做法**:
  - **直接做**:lead 自己改。小改动不需要任何 fusion 工具。想记进台账、或者想让引擎跑检查,就用 `fusion_plan` 的 direct 形式开始、`fusion_accept` 结束;提交照常由 lead 做
  - **派工**:任务里有 `mechanical`、`verify` 工作时,派给助手
  - 什么时候直接做:工作项全是 `judgment`,或者改动很小(一两个文件、很快能做完)

### 4.2 工作项类型
| 类型 | 含义 | 例子 | 默认负责人 |
|---|---|---|---|
| `judgment` | 结果取决于取舍或品味 | 用户能感知的设计、交互、文字和数值;模块之间的接口和数据格式;对歧义的取舍 | lead |
| `mechanical` | 决定都已给出,剩下的是工程 | 按已定接口实现、迁移、重构、删除、补测试 | 助手 |
| `verify` | 运行和观察 | 跑慢测试、lint、类型检查、盯 CI | 助手 |
| `explore` | 读和找 | 定位相关代码、查 API、列出约定和坑 | 助手 |

- **判定 `judgment` 的三句话**,有一个"是"就是 `judgment`:结果会被用户看到、或被其他模块依赖吗?两个能干的工程师会做得不一样吗?做错了是否只能靠审美发现?
- **转换**:lead 可以把 `judgment` 工作写成足够具体的决定,再转成 `mechanical` 派出去;转换时必须新增或引用对应的决定
- **样例**:`mechanical` 工作项可以写 `follows: W1`,表示"照 W1 的样子做"。W1 必须是 lead 负责的 `judgment` 工作项,并且在派工前已经提交。助手照着扩展,偏离样例的地方要写进报告的"自定的选择"

### 4.3 意图记录
- 每条决定:编号和版本(`D12@2`)、类别(`experience` 体验 / `interface` 接口 / `rule` 规则 / `constraint` 约束)、内容、理由、影响的文件或模块、状态(有效 / 被取代)
- 可选字段:来源(用户原话)、样例、反例、考虑过但否决的方案、**检查命令**
- 带检查命令的决定,每个候选都要跑这条检查。能做成检查的就做成检查(例如接口快照、文案快照、"界面层不 import 数据库")
- 决定只以事件的形式存在事件库里;`fusion/intent.md` 是生成的,给人和助手读,跟踪进 git,让代码和当时的意图一起演进。它用固定格式生成,事件库丢失时引擎能从它恢复当前的决定
- 只由 lead 通过工具修改;助手只读
- 任务和工作项按版本引用决定。决定升版本后:
  - 引用旧版本的进行中任务,在状态里标出来
  - 这些任务的候选证据失效,lead 改引用新版本后才能验收
- 项目配置一份**用户能感知的文件**清单(例如 `ui/**`、文案、数值配置)。助手改到这些文件,不管 lead 怎么标类型,都会发信号

### 4.4 决定债
- 助手的报告必须列出**自定的选择**:没人要求、但它自己做了的选择(选了什么、其他选项、为什么、影响的文件)
- 每条记成 `T3.E1`。验收前,lead 必须逐条处理:认可、升格为决定、或者驳回(驳回就是一条修改意见)
- 未处理的决定债挡住验收
- 漂移最常藏在没写下来的小决定里。"产生了多少决定债、升格和驳回了多少"本身就是一个漂移指标
- 交叉核对:改了用户能感知的文件,却报告没有任何自定的选择,也会发信号

### 4.5 任务单的三组边界
- **必须遵守**:引用的决定、规则、接口
- **可以自己定**:明确交给助手的范围(例如内部变量名、私有函数的拆法)
- **必须上报**:碰到就要提阻塞问题的情况(例如要改公开接口、要改用户能看到的文字)
- lead 写完计划后自查一句:两个能干的工程师照这份计划各做一遍,用户分不出差别吗?分得出来,就缺一个决定

### 4.6 验收检查
- `command`:一条命令加期望(退出码、输出匹配、通过的测试数),由引擎运行
- `manual`:程序证明不了、要人看的(界面、手感)。写明看什么、什么算通过、由谁签字:
  - `signer: lead`:lead 看过后在验收时签字,写下看到了什么
  - `signer: user`:用户在 Fusion 栏里点通过或不通过;没有栏的时候,lead 原样记录用户的话,签字人记为 `user-via-lead`
  - 签字是事件,绑定候选
- 每个 `mechanical` 工作项至少对应 1 条检查;影响用户能感知内容的工作项至少引用 1 条 `experience` 决定

### 4.7 工位和续用
lead 从不接触会话编号。续用的事由引擎记住、自动接上。

- **工位** = 一个 Codex 会话 + 一个专属工作目录(git worktree,放在项目文件夹旁边,例如 `HEX-fusion/`)。alpha 只有 1 条工作线,所以同一时间只有 1 个在用的工位
- **工位表**(由事件算出):
  - 名字(`main#2`)、Codex 会话编号、模型、推理强度、快速档、工作目录
  - 接替的上一个工位、做过的任务、最近一次请求的输入量(约等于当前上下文)
  - 状态:空闲、运行中、已退役
- **会话编号从哪来**:`codex exec --json` 开头的会话事件。引擎写进事件库后,所有续用都用它。工具的参数和返回值里只有工位名,没有会话编号
- **自动接上的三种情况**:
  1. 同一个任务里:探索、实现、修改请求、修检查失败、回答问题后继续,都续用同一个工位,上下文是连着的
  2. 下一个任务、下一个阶段:默认续用这条工作线的工位。lead 不需要找任何东西
  3. lead 自己换了对话(新对话、上下文压缩、第二天接着做):`SessionStart` 钩子把进行中的任务、工位在做什么、等待列表、相关决定注入给新的 lead,lead 接着调用工具即可
- **换工位**(引擎决定,lead 在状态里看到一行说明):
  - 当前上下文超过模型备注里上下文上限的 60%
  - 新任务的文件范围和这个工位做过的文件几乎不重叠(换了主题)
  - Fusion 栏里换了助手模型(从下一个任务起生效)
  - 续用失败(会话找不到或报错):记 `station_lost`,自动换
- **交接摘要由引擎拼**:新工位的第一条提示来自数据,包括相关决定(最新版本)、做过的文件和最后的候选、未处理的决定债、报告里记下的已知问题。不让臃肿的旧会话自己写
- **lead 的对话也记一笔**:钩子的输入里带有 Claude Code 的会话编号,引擎记成 `lead_session` 事件。用途:台账区分不同的 lead 对话;用户想知道"T3 是在哪个对话里规划的"时能查到。只用钩子给的数据,不读 Claude Code 的任何文件

### 4.8 信号
引擎根据事件自动产生信号,送到 lead。信号只有 5 个,lead 决定怎么处理:
| 信号 | 触发 | 建议的处理 |
|---|---|---|
| `check_failed` | 同一条检查在助手修了 2 次后仍然失败 | 接管、改计划或提修改意见 |
| `blocked` | 助手提了阻塞问题,本次运行已结束 | 回答后自动续用 |
| `perceivable_touched` | 改了用户能感知的文件或 `judgment` 工作项的文件;或者改了这些文件却没报告任何自定的选择 | 审查时必看 |
| `violation` | 做了禁止的操作;或者派工前的测试在新代码上失败 | 不能验收,直到 lead 处理,必要时先问用户 |
| `stalled` | 运行一段时间没有新事件,或者运行中断 | 查看,然后续用或取消 |

## 5. 架构

### 5.1 总览
```
用户 ⇄ Claude Code 会话(lead = Claude)
        Fusion 栏(mod) · 注入(hooks) · 通知(monitor) · 方法(skill)
        │ fusion_* 工具(MCP)
┌───────▼──────────── fusion-core(Python 标准库)─────────────┐
│ serve:MCP 工具 + 运行监督                                    │
│ 命令 → 校验 → 状态机 → 事件库 fusion.db(sqlite3,唯一写入口)│
│ 工位表 · 检查流水线 · 集成                                    │
└───────┬─────────────────────────────┬────────────────────────┘
        │ codex exec --json / resume   │ git:任务分支、候选、快进
┌───────▼──────┐  写文件  ┌────────────▼─────────┐  验收后快进  ┌──────────────┐
│ Codex 工位    │ ───────▶ │ 工位目录(worktree) │ ──────────▶ │ 项目(main)   │ ◀ lead 直接改
└──────────────┘          └──────────────────────┘              └──────────────┘
```
图形版见 `v5.0.0-a-architecture.svg`。

### 5.2 为什么引擎和外壳分开
- 引擎可以用假 Codex 做完整的自动测试,不需要 Claude Code
- 引擎可以单独拿去跑基准,把"lead"换成脚本化的对照组
- 外壳很薄:工具走标准的 MCP,拦截和注入走官方钩子,mod 只做界面和用量。Claude Code 的接口变了,只改外壳

### 5.3 数据各归各处
| 数据 | 归属 | 说明 |
|---|---|---|
| 流程状态(任务、决定、问题、候选、信号、用量) | 事件库 `fusion/fusion.db` | 只由引擎写 |
| 代码 | git | 候选是任务分支上的提交;验收后进 main |
| 当前的意图决定 | `fusion/intent.md` | 由事件库生成,跟踪进 git |
| 原始日志 | `fusion/runs/` | Codex 原始事件、输出、检查日志 |

## 6. 插件外壳

### 6.1 组件
| 组件 | 用途 |
|---|---|
| MCP 服务器 `fusion-core serve`(stdio) | 提供 lead 的工具;同时监督助手运行 |
| hooks | `SessionStart`(新对话、续接、清空、压缩后):注入角色说明、进行中的任务、工位、等待列表、相关决定;`UserPromptSubmit`:一行状态;`PreToolUse`(Edit、Write):编辑提示 |
| monitor | 运行 `fusion-core events --follow --audience lead`,把"候选待审""阻塞问题""信号"变成通知 |
| mod | Fusion 栏;从 `turn.step` 记 lead 用量;`/fusion` 即时开关 |
| skill | lead 的方法:用三句话分类、写决定完整的计划和三组边界、先做样例、三层审查、处理决定债。只在 Fusion 打开时生效 |
| 命令 `/fusion` | 开关和设置;没有 mod 时由命令调用 `fusion-core config` 实现 |
| `bin/` | `fusion-core` 的启动脚本,插件启用时在 PATH 里 |

### 6.2 Fusion 栏
- `/fusion` 打开或关闭 Fusion。打开时,输入框上方显示一条 Fusion 栏
- 栏里可选:助手模型、推理强度、快速档(Codex 的 `service_tier=fast`)。lead 的模型就是会话本身的模型,用 Claude Code 自带的模型选择器
- 栏里显示一行状态和一行用量:"T3 运行中 · 1 个问题待答 · 决定债 2""本任务 lead 1.2M · 助手 4.8M(缓存 96%)"
- 有 `signer: user` 的人工检查待签时,栏里显示通过和不通过两个按钮
- 栏的设置存在项目的 `fusion/local.json`(不进 git),下次打开沿用
- 限制:Claude Code 的原生模型选择器不能被插件修改,所以 Fusion 不能作为选择器里的一个"模型"出现
- 台账按钮和面板放到 5.0.0-b

### 6.3 lead 的工具
| 工具 | 作用 | 前置状态(见 7.2) |
|---|---|---|
| `fusion_intent` | 新增、修改、取代决定;可带来源、样例、反例、否决方案、检查命令 | 任何时候 |
| `fusion_plan` | 建任务或改任务单;direct 形式只写目标 | 新建;或在 `planned`、`in_review` 时改版 |
| `fusion_explore` | 只读提问,最多 3 个,答案以通知送达 | 工位空闲时用工位(上下文留给后面的实现);工位忙时开一个临时的只读会话 |
| `fusion_delegate` | 派工作项;有 `follows` 的工作项要写明样例的提交 | `planned`;或 `in_review` 时补派 |
| `fusion_answer` | 回答问题;可选"升格为决定" | 阻塞问题:`blocked`;非阻塞问题:任何时候 |
| `fusion_review` | 取交接视图,`tier` 1~3,默认 2 | `in_review` |
| `fusion_request_changes` | 审查意见;可以驳回决定债;不强制引用编号,但每条要写期望的结果 | `in_review` |
| `fusion_accept` | 验收:点名要验收的候选;认可或升格剩余的决定债;签人工检查 | `in_review`;direct 任务在 `planned` |
| `fusion_reject` | 退回:删任务分支,证据留下 | `in_review`、`blocked` |
| `fusion_cancel` | 停止当前运行和任务 | 非终态 |
| `fusion_takeover` | 接管工作项:停止运行,可选把半成品搬到 lead 的工作目录 | `running`、`blocked`、`in_review` |
| `fusion_status` | 任务、工作项、等待列表、工位、信号 | 任何时候 |

- 参数或状态不合格时,工具直接返回错误和原因,lead 当场修正
- 重复调用:已经到达目标状态的,返回原来的结果,不重复执行(例如对已接受的任务再调 `fusion_accept`)
- 工具的说明文字要短:Fusion 关闭时它们也在 lead 的上下文里,只是会返回"Fusion 未打开"

### 6.4 编辑提示
- 有了独立的工位目录,lead 的编辑不会和助手的写入撞在一起,所以不需要拦截
- lead 用 Edit、Write 改到正在派工的文件范围时,`PreToolUse` 钩子给一段提示(不阻止):这些文件助手也在改,验收时可能要合并
- 真正的保护在验收时的集成检查(见 7.7)

### 6.5 注入的内容和上限
- `SessionStart`:lead 角色说明(不超过 60 行)+ 当前状态和相关决定(不超过 40 行;决定太多时只列编号和标题,全文用 `fusion_status` 看)
- 上下文压缩后同样注入,这是 lead 一侧"设计记忆"的恢复方式
- 每次提问:一行状态("T3:运行中,1 个问题待答")
- 每轮注入的文字都占上下文,所以设硬上限,由测试检查

### 6.6 宿主能力和降级
| 能力 | 依赖 | 缺了怎么办 |
|---|---|---|
| lead 的工具 | 插件的 MCP 服务器 | 必需 |
| 注入、压缩后恢复 | `SessionStart`、`UserPromptSubmit` 钩子 | 必需 |
| 编辑提示 | `PreToolUse` 钩子 | 没有提示;集成检查兜底 |
| 通知 | monitor | 等待列表靠每次提问注入的状态行 |
| Fusion 栏、即时开关 | mod(桌面端) | `/fusion` 命令带参数;状态行照常注入 |
| lead 用量 | mod 的 `turn.step` | 台账里 lead 用量记为"未知" |
| 用户签字按钮 | mod | lead 原样记录用户的话,签字人记为 `user-via-lead` |

## 7. fusion-core 引擎

### 7.1 事件库
- 文件:项目里的 `fusion/fusion.db`,标准库 `sqlite3`,WAL 模式
- 表:`events(seq, ts, v, type, task, item, actor, data)`。`v` 是事件格式的版本,重放时按版本升级旧事件
- **唯一写入口**:每条命令在一个 `BEGIN IMMEDIATE` 事务里完成"读状态 → 校验 → 状态机 → 追加事件"。mod、钩子、monitor 都不直接写库,要写就调用引擎命令
- 主要事件:`task_planned`、`plan_revised`、`intent_changed`、`lead_session`、`station_created`、`station_retired`、`station_lost`、`run_started`、`run_progress`(摘要)、`question_asked`、`question_answered`、`run_ended`、`candidate_created`、`check_ran`、`signal`、`review_viewed`、`changes_requested`、`debt_resolved`、`manual_signed`、`integration_ran`、`accepted`、`rejected`、`cancelled`、`takeover`、`usage`、`config_changed`
- 任务状态、工位表、等待列表、决定债、交接视图都由事件重放得到;结果可以缓存,但缓存不是数据来源
- `fusion-core events --export` 导出 JSONL 给人看
- **对账**:`serve` 启动时检查进行中的运行:
  - 进程还在 → 接着监督
  - 进程已结束、输出完整 → 继续走检查流水线
  - 其他 → 记 `stalled`,任务回到 `in_review`,由 lead 决定续用还是取消
  - 同时核对工位目录的分支和最新候选是否和记录一致,不一致就发信号
- **监督权**:同一个项目同时开了两个 `serve` 时,只有拿到监督权(库里一行带心跳的记录)的那个监督运行,另一个只提供工具

### 7.2 状态机
```
planned ─delegate─▶ running ─运行结束─▶ checking ─通过─▶ in_review
                     │  ▲                   │ 失败,助手修(最多 2 次)
            阻塞问题 ▼  │ 回答              └──▶ running
                    blocked
in_review ─request_changes─▶ running
in_review ─accept─▶ integrating ─通过─▶ accepted
                        └─冲突或检查失败─▶ in_review(带信号)
修了 2 次仍失败 ─▶ in_review(带 check_failed)
任何非终态 ─cancel─▶ cancelled      in_review / blocked ─reject─▶ rejected
running / blocked / in_review ─takeover─▶ planned(改为 direct)
direct 任务:planned ─accept─▶ accepted
```
- 终态:`accepted`、`rejected`、`cancelled`
- lead 负责的工作项没有运行,只记"完成于哪个提交"(派有 `follows` 的工作项时,或验收时)
- 每个工具的前置状态见 6.3;状态不对就拒绝并说明当前状态
- 同一个任务已经提过 3 轮修改意见时,第 4 次 `request_changes` 被拒绝,要先问用户(见 10.1)

### 7.3 命令行接口
所有命令读 JSON(参数或标准输入),输出 JSON:
```
fusion-core init                         建 fusion/、默认配置、.gitignore
fusion-core serve                        MCP 服务器 + 运行监督(由插件启动)
fusion-core plan | intent | delegate | explore | answer | review |
            request-changes | accept | reject | cancel | takeover | status
                                         和 lead 的工具一一对应
fusion-core events --follow --audience lead   给 monitor
fusion-core events --export FILE         导出 JSONL
fusion-core config get | set             给 /fusion 和 Fusion 栏
fusion-core usage record                 给 mod 记 lead 用量
fusion-core ledger [--task T3]           文字台账
fusion-core preflight                    环境预检:Codex、git、工位目录、测试命令
```

### 7.4 任务单校验
- 每个工作项有类型、负责人、文件范围(glob)
- 每个 `mechanical` 工作项至少对应 1 条验收检查
- 检查是 `command`(有期望)或 `manual`(写明看什么、什么算通过、谁签字)
- 影响用户能感知内容的工作项,至少引用 1 条 `experience` 决定
- 引用的决定存在、有效、版本是最新的
- 不同负责人的工作项,文件范围不重叠
- `follows` 指向 lead 负责的 `judgment` 工作项
- 三组边界都写了(可以为空,但要写)
- 允许改动的测试要单独列出(`tests_may_change`),并引用决定
- 成功标准之间是否自相矛盾无法完全自动判断;校验器只做能确定的检查,其余交给 lead 的自查

### 7.5 一次助手运行
1. **准备工位**:找到这条工作线的工位(没有就新建 worktree,复制配置里列出的未跟踪文件,例如 `run/eula.txt`);从当前 main 开任务分支 `fusion/T3`(已有任务分支就接着用)
2. **生成提示**:任务单、三组边界、相关决定(带版本)、样例的提交、模型备注、助手规则;新工位再加交接摘要
3. **启动**:`codex exec --json`(新工位)或 `codex exec resume`(已有工位),工作目录是工位目录
   - 子进程只继承标准输入、输出、错误三个文件,输出直接写进 `runs/<run>/`。这是 v4 在 Windows 上解决管道挂住(7~34 分钟)的做法,保留
   - 绝不继承 `serve` 自己的标准输入输出(那是 MCP 的通道)
   - 子进程独立于 `serve`:Claude Code 关了,Codex 照样跑完,下次 `serve` 启动时对账
   - 启动前从环境变量里去掉 `CLAUDE*`、`ANTHROPIC*`
4. **提问**:
   - 非阻塞问题:助手按自己的推荐继续,这个选择自动记进决定债。lead 事后回答的和助手选的不一样,就自动变成一条修改意见
   - 阻塞问题:助手输出问题后结束本次运行;任务进入 `blocked`,通知 lead;lead 回答后引擎带着答案续用工位
   - 没人回答的阻塞问题留在等待列表里,不自动开 lead 的回合,也不超时自动继续(阻塞问题本来就是"猜错代价大"的问题)
5. **结束**:校验报告格式(不合格就续用一次让助手补)→ 引擎把改动提交成候选 → 跑检查流水线 → 不过就把失败输出交给助手修(最多 2 次,每次产生新候选)→ 进入 `in_review`,通知 lead

### 7.6 检查流水线
| 检查 | 什么时候 | 说明 |
|---|---|---|
| 项目测试、lint | 每个候选 | 项目配置的命令;输出存档,提取失败行和测试数 |
| 验收检查 | 每个候选 | 任务单里的 `command` 检查,加上引用的决定带的检查命令 |
| 旧测试跑新代码 | 候选改了测试文件时 | 把派工前的测试文件放回候选上再跑一次。失败就是 `violation`,除非这个测试在 `tests_may_change` 里。测试文件的改动一律进第 2 层 |
| 范围 | 每个候选 | 对照工作项的文件范围,超出的进第 2 层 |
| 用户能感知的文件 | 每个候选 | 对照配置的清单和 `judgment` 工作项,命中就发 `perceivable_touched` |
| 禁止操作 | 每次运行 | 见下面三层 |
| 环境错误 | 测试失败时 | 输出匹配证书、网络类错误时原样重跑 1 次,不交给助手 |
| 集成检查 | 验收时 | 合并 main 之后再跑测试、lint、验收检查(见 7.7) |

**禁止操作分三层:**
1. **事前阻止**(Codex 自己的机制):沙箱只允许写工位目录;不弹审批;网络按配置,默认关。git 的元数据在工位目录之外,所以助手提交、切分支、推送都写不进去
2. **事后检测**(引擎):扫描命令记录和 diff,匹配配置里的规则(关证书检查、跳过钩子、改 CI 配置、删测试等),命中就是 `violation`
3. **疑似风险**:规则之外的可疑改动(新加的网络地址、改了构建配置)列进第 2 层,不阻塞

### 7.7 验收、退回、取消、接管
**验收(`fusion_accept`)**
1. lead 点名要验收的候选(例如 `T3.c2`)。引擎核对:检查证据属于这个候选;任务单版本、引用的决定版本、检查配置都没变;决定债已经全部处理;人工检查已签字。任何一项对不上,旧证据失效,要重跑检查
2. main 前进过的话,在工位目录里把 main 合进任务分支。有冲突 → 回到 `in_review` 并说明(lead 可以派"解决冲突",或者接管)
3. 在合并结果上跑集成检查
4. 把结果压成一个提交(父提交是当前的 main,提交信息带任务、候选、决定版本、运行编号),让 main 快进到它。lead 的工作目录里有冲突的未提交改动时,git 会拒绝,引擎停下并说明
5. `intent.md` 有变化时单独提交
6. 删任务分支;工位回到空闲;证据留在 `runs/`

**direct 任务的验收**:在 lead 的工作目录上跑项目测试、lint 和验收检查,记录结果;不合并,也不替 lead 提交。

**退回(`fusion_reject`)**:删任务分支,工位目录回到 main;候选的 diff 和日志留在 `runs/` 作为证据。

**取消(`fusion_cancel`)**:结束整个 Codex 进程树,丢掉工位里没提交的改动,其余同退回。

**接管(`fusion_takeover`)**:针对当前这次运行里的全部工作项。停止运行;`bring: true` 时,把任务分支相对起点的改动搬到 lead 的工作目录(不提交;有冲突的文件列出来,不覆盖);工作项改由 lead 负责,之后按直接做的方式收尾。

### 7.8 交接视图
| 层 | 内容 |
|---|---|
| 1 | 摘要:检查结果、信号、待答问题、决定债数量、每条相关决定的实现说明 |
| 2(默认) | 第 1 层 + 决定债明细 + 这些文件的 diff:`judgment` 工作项、用户能感知的文件、测试文件、被检查或信号标出的文件、范围外的文件 |
| 3 | 完整 diff、原始日志的路径 |

- **记录问题在哪一层发现**:每条修改意见,引擎记下 lead 之前看过哪几层、意见里提到的文件是否在第 2 层里
- 验收后才发现的问题:新任务的任务单写 `fixes: T3`,算作漏检
- 有了数据再决定默认给第几层

### 7.9 助手报告格式
在 v4 的 JSON 报告上扩展:
- `summary`
- `items`:每个工作项的状态、对应检查、简述
- `decisions`:每条引用的决定(带版本)是怎么实现的;偏离的写理由
- `choices`:自定的选择(决定债),必填,没有就写空列表
- `questions`:问题、是否阻塞、选项和推荐;非阻塞的写明已按哪个选项继续
- `assumptions`、`downstream`、`problems`

### 7.10 复审(可选,默认关)
- 打开后,lead 审查前引擎用 `codex review` 对照意图记录和任务单复审候选
- 复审只输出"疑似偏离"的条目,每条指向文件和决定,放进第 2 层,不进第 1 层
- 默认关的原因:Codex 审 Codex 的盲区相关,噪声多。是否打开看基准数据

## 10. 政策和使用约束

### 10.1 遵守 Anthropic 的政策
插件本身、以及插件让 Claude 做的事,都不能违反 Anthropic 的政策(消费者条款、使用政策、Claude Code 的法律与合规说明)。落到设计上:
- **只做 Claude Code 的普通使用。** 只用官方的插件组件(MCP、hooks、monitor、skill、mod、命令)。不在 Claude Code 之外调用或驱动 Claude;插件不调用 Claude 的 API,也不需要 API 密钥
- **不经手凭据。** 不收集、不转交、不中转任何人的登录凭据;订阅登录凭据不交给任何其他工具
- **工作来自用户。** 每段工作都来自用户的一个请求。为完成这个请求,Claude 可以处理后续事件(助手跑完、助手提问),但插件不替 Claude 开新的工作:
  - 不用定时器发起回合
  - 不用 mod 的 `$.prompt.submit`、`$.session.send` 等接口自动发消息
  - 不做无限循环:检查失败最多让助手修 2 次;同一个任务的修改意见超过 3 轮,停下来问用户
- **不绕开 Claude Code 的安全机制。** 钩子只注入和提示,不替用户批准权限,不关闭权限提示和沙箱。注入给 lead 的文字只讲方法和状态,不覆盖 Claude 自身的规则;注入的内容都能在插件文件夹里看到
- **用量按正常的个人使用。** 不绕开订阅的用量限制;不共享账号。基准和预实验的每次运行都在用户自己开的会话里
- **名字和说明。** 插件名不用 Anthropic、Claude 的名字和标志;说明里不暗示是官方出品或得到官方认可
- **什么时候检查。** 政策会更新,所以在这几个时间点重新读一遍相关政策,对照本节逐条检查,结果写进里程碑记录:
  - M2 第一次装插件之前
  - 每个里程碑完成时
  - 将来发布到插件市场之前
- 调研和依据见 `lyfusion/suggestions/2026-11-06-plugin-research.md`

### 10.2 用户自己的规则(比政策更严)
- Claude 只在用户自己打开的 Claude Code 会话里运行,不设置无人值守的 Claude 运行
- 插件只运行自己安装目录里的代码;状态都放在项目文件夹;不使用插件数据目录;不读取 Claude Code 的其他配置和记录
- 不读取 Codex 的登录文件;不经手任何密码或密钥
