# lyfusion v5.0.0-aq:lead 只留 4 个动作

> 2026-11-07。依据 `v5/aq-brief.md`(Lily 定的)。从 v5.0.0-a(`70cbf28`)收窄而来;v5.0.0-a 的工程设计 `v5.0.0-a-engineering.md` 不改,本文只写差别。

## 1. 为什么
- v5.0.0-a "变大了,没变深":lead 面前有 12 个工具、带工作项和边界的任务单、意图记录、决定债、3 层审查视图。每个概念每个任务都要 lead 付调用和上下文
- v4 的形状(Cognition Fusion 图)质量和成本都好:探索 → lead 读片段 → 计划 → 助手实现、测试、lint → lead 审查 → 修改 → 验收
- 做深模块:接口只有 4 个动作,v5 引擎的能力(工位、候选、检查、自动修、集成)都藏在里面

## 2. lead 看到的全部
SessionStart 钩子在 Fusion 开着时注入下面的使用说明;`fusion-core on` 也打印它。全文(≤20 行):

```text
lyfusion 已开:这个项目的代码活交给 Codex 助手做,你(lead)只做 4 件事。
每条命令都在 Bash 里用 run_in_background 运行。命令自己等到有结果才结束,结束时会叫醒你:
不要开 Monitor、不要 sleep、不要轮询。醒来后直接读结果文件。
1. 探索:fusion-core explore - <<'EOF' …… EOF
   写用户的任务原话(一字不改)和你想知道的,最多 3 条,编号 Q1~Q3。结果:fusion/explore.md
2. 派工:fusion-core delegate - <<'EOF' {计划} EOF   续用探索的会话。结果:fusion/review.md
   计划是 JSON:{"goal": "一句话", "brief": "Markdown 正文", "checks": [{"run": "命令", "expect": 0}], "scope": ["src/**"]}
   checks、scope 可省。brief 推荐小标题:目标、决定、不要做的事、已知的坑。
3. 修改:fusion-core revise - <<'EOF' 修改意见 EOF   自由文字,助手的问题也在这里回答。结果:fusion/review.md
4. 验收:fusion-core accept   合并、重跑检查、压成 1 个提交、快进主分支。
跨任务都要守的设计决定写进 fusion/decisions.md(普通文件,直接编辑),引擎每次派工把全文带给助手。
审查包不够看时,用 Read 看具体文件。看进度 fusion-core status;放弃任务 fusion-core cancel。
```

一个派工任务 lead 约 5 次调用:explore → Read 探索包 → delegate → Read 审查包 → accept;每轮修改加 2 次(revise → Read 审查包)。

## 3. 命令
| 命令 | 输入 | 阻塞到 | 结果 |
|---|---|---|---|
| `explore [文件\|-]` | Markdown:任务原话和问题 | 探索包写好 | `fusion/explore.md` |
| `delegate [文件\|-] [--task T]` | 计划 JSON | 审查包写好(自动修、检查都做完) | `fusion/review.md` |
| `revise [文件\|-] [--task T]` | 自由文字 | 新的审查包写好 | `fusion/review.md` |
| `accept [--task T] [--waive "原因"]` | — | 集成做完 | 提交编号,或退回原因 |
| `status`、`cancel [--task T]`、`on`、`off`、`config`、`preflight`、`ledger` | | | 不进使用说明的主流程 |

- `-` 从标准输入读(heredoc),按 UTF-8 读字节再解码;文件也按 UTF-8(可带 BOM)读
- `--task` 省略时用当前任务。同一时刻只有 1 个进行中的任务(沿用 v5.0.0-a 的 WIP 1)
- 每条命令自己当监工:拿监督租约、跑 supervisor 的 tick,直到目标状态;拿不到租约(别的命令在监督)就只看事件。v5.0.0-a 的 `wait` 循环挪到这里
- 任务已有运行在进行(比如上一次命令被中断),explore/delegate/revise 不重开运行,接着等它
- 结束时打印:结果文件路径、2~4 行摘要、下一步可用的命令
- 退出码:0 结果写好了(检查不过也是 0,审查包里写);1 输入有误,什么都没开始,报错说清怎么改;2 要 lead 处理、没有结果文件(Codex 起不来、长时间无进展、修改轮数到上限、集成冲突等),报错说清下一步
- 每个结果在 `fusion/tasks/T编号/` 留一份历史(`explore.md`、`review-1.md`、`review-2.md`……)。`fusion/explore.md`、`fusion/review.md`、`fusion/tasks/` 写进 `fusion/.gitignore`(和 `runs/` 一样),免得 lead 顺手提交进项目;`fusion/decisions.md` 进 git

## 4. 计划:4 个字段
```json
{"goal": "一句话", "brief": "Markdown", "checks": [{"run": "命令", "expect": 0}], "scope": ["src/**", "tests/**"]}
```
- 只校验这 4 个字段:`goal` 非空的一行字;`brief` 非空字符串,内容不校验;`checks` 每条有非空 `run`,`expect` 可省(默认退出码 0),写整数是期望的退出码,写字符串是输出里要出现的文字(正则,且退出码为 0);`scope` 是 glob 列表。多出别的字段就报错,列出允许的 4 个
- 原则:程序要执行或检查的才结构化(checks、scope),助手要理解的用自由文字(goal、brief)
- 项目配置里的 `test`、`lint` 每次都跑,计划的 checks 跑在它们之后
- `goal` 用在压缩提交的说明和 `status` 里

## 5. 探索包
引擎给助手的探索提示(只读沙箱)要求:先复述任务、列不确定的地方;相关代码片段(`文件:起止行`、为什么相关、原文 ≤15 行,按重要程度排);按 Q1~Q3 回答;现有约定和坑;全文 ≤150 行;不写实现方案。lead 的原文整段附在提示里。
探索包 = 头 2 行(任务编号、助手会话)+ 助手的原文。探索的 Codex 会话由引擎记住,delegate 续用它。

## 6. 审查包:只有一层
按顺序:
1. **检查**:每条一行(名字、命令、通过与否、退出码);没过的附输出最后 ≤20 行。另写自动修了几次、旧测试跑新代码的结果
2. **违规**(只在有时出现这一节):禁止操作;测试被改弱(派工前的测试在新代码上失败)。这一节末尾直接写怎么放行:`accept --waive "原因"`,有禁止操作时原因里要写用户的原话。lead 一次调用就能验收,不用先被拒一次
3. **助手的问题和自定的选择**:状态(做完/停下及原因)、摘要、问题、自定的选择、没做完和已知的问题
4. **改动**:`diff --stat`,scope 之外的文件标"(范围外)";diff 不超过 400 行就全文附上,超过只列文件名

不够时 lead 用普通的 Read 看文件。助手的最终报告字段收窄为 `status`(done/blocked)、`summary`、`questions`、`choices`、`problems`。

## 7. 修改和验收
- 修改意见是自由文字,同一个 Codex 会话续做。最多 3 轮(`max_change_rounds`),到上限退出码 2,先问用户
- 验收拒绝的情况:检查没全过(只有环境类错误时可以 `--waive` 写原因放行);有违规又没 `--waive`(禁止操作要写用户的原话;测试被改弱,lead 确认是计划要的行为变化,写原因);助手停下提问还没用 revise 回答
- 问题和自定的选择只列在审查包里,不强制逐条处理,也不拦验收
- `reject` 并进 `cancel`:先把任务的 diff 存进 `fusion/runs/` 当证据,再停运行、清工位、丢弃候选

## 8. 防设计跑偏:`fusion/decisions.md`
只有这一个普通文件。`on` 时没有就建一个带两行说明的空文件。lead 直接编辑;引擎每次给助手的提示(探索、派工、修改、自动修)都附上全文。没有版本、没有引用、没有决定债。

## 9. 留在引擎里(lead 看不见)
Codex 会话续用;工位目录和任务分支;候选提交;检查失败自动修 ≤2 次;环境错误原样重跑;禁止操作扫描;旧测试跑新代码;验收时合并、重跑检查、压成 1 个提交、快进 main;上下文太大换工位;台账记用量;脱敏;启动 Codex 去掉 `CLAUDE*`、`ANTHROPIC*` 环境变量。
