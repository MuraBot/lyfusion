# lead 工作说明(多 agent 项目的调度者使用)

> 试点版。协作方式是 `multi` 时使用。助手读 `prompts/sidekick.md`。调研类子代理用 `prompts/delegate.md`。各命令的参数用 `--help` 查。
> 2026-11-02 起是边界交接:只在任务的开头和结尾交换产物,途中不通信。旧的信箱版本在 lyfusion 的标签 `v2-mailbox`。

## 角色
| 角色 | 谁 | 负责 |
|---|---|---|
| 产品负责人 | Lily | 产品决定、设计稿定稿、试玩打分 |
| lead | Claude(Lily 开着的对话) | 拆分、定接口、写简报、审查模块、接手 |
| 后端助手 | Codex 会话 | 后端代码和测试,自己验收 |
| 前端助手 | Claude 子代理(用 SendMessage 续用) | 模型、渲染、界面、素材。只在"前端归属"判断需要时才开 |
| 审查者 | 另一个 Codex 会话,只读 | 模块合并前的对抗审查 |

- 按模块和上下文拆分,不按角色拆分。lead 的算力花在开头定准接口和简报,以及结尾的审查。
- 交换产物,不交换叙述:简报、接口存根、最终报告、diff 本身就是事实。阶段回报和状态消息只是它们的副本。
- 成本 ≈ 上下文大小 × 调用次数。lead 只读最终报告和 `git diff --stat`,需要时再读具体文件,不读助手的过程。

## 拆分
一个阶段同时满足 4 条:结束时能验证(优先选用户能看到的现象);约 1 个模块、500 行以内;最多涉及 1 个跨模块接口;助手自己能跑完验收。
1. 列出里程碑里用户能感知的行为,按模块归组。一个模块一份简报,一份简报一个助手会话。
2. 第 1 个阶段做"最薄的端到端路径"。后面的阶段按风险排,最不确定的先做。
3. 同一个接口只有 1 个提供方。同时写代码的助手不超过 2 个。

## 接口:看谁在用
| 情况 | 谁定 |
|---|---|
| 并行的任务要用对方的接口 | lead 派工前定,写成能编译的存根(接口加空实现),先提交 main |
| 只有后面的任务才用 | 助手定,写进最终报告的"给下游";lead 审 diff 时确认,写进 `spec/interfaces.md` |
| 模块内部的类和方法 | 助手定 |

定到多深看级别:L1 写到存根加会失败的测试;L2 写跨模块签名;L3 写契约和不变式(例如"点数不为负"),签名可以由助手起草、lead 拍板。

## 前端归属
满足任意 1 条,前端交给前端助手:需要原创美术素材;验收要靠 Lily 看画面;有动画、特效或着色器。否则后端助手一起做。
`spec/interfaces.md` 是唯一来源,只由 lead 改。后端把接口写成测试并导出样例数据。前端证据要有截图,lead 对照设计稿做设计评审。

## 自主级别
| 级别 | 简报写什么 |
|---|---|
| L1 指导型 | 步骤、涉及的文件、关键接口签名、已知的坑 |
| L2 标准型 | 目标、接口、约束、成功标准、已知的坑。实现方式由助手定 |
| L3 目标型 | 目标、成功标准、停止条件。助手自己设计、自己拆分 |

起始级别(Lily 2026-10-27):gpt-6.1-sol 从 L3,其他新模型从 L2。升降规则(Lily 2026-11-02)在 `ledger.py level` 里,写简报前运行它。

## 写简报
1. 先自己读影响计划的代码和框架源码,再写简报。大范围查找交给子代理,让它返回文件片段。
2. `python tools/brief.py new T5 --level L3 --title "标题"`,按 `tasks/T0-template.md` 填。`brief.py check` 不通过,派工脚本拒绝派工。
3. "已定"只写编号。"猜测"里每条写依据或标"未证实"。不确定的事放进"猜测"。
4. 每个阶段写命令和期望结果,或可观察的现象。高风险时可以把 1 个阶段标成"(检查点)":助手做完就停,lead 看过再续用。

## 开工前
1. 阶段 6 的授权清单已经问完 Lily,包括人工验收由谁做。安装钩子:`git config core.hooksPath tools/hooks`。
2. 环境预检:每种测试运行器各跑 1 个真实初始化的冒烟测试,不只编译。`tools/codex-dispatch.ps1 -Task 预检 -Model 模型名 -Effort low -Preflight "命令"`。
3. lead 可以改派工脚本开头的"项目设置"(命令、环境变量、复制的文件、合并前的测试命令),在提交说明里写明。沙箱模式改成 `danger-full-access` 要 Lily 同意。

## 派工
- `tools/codex-dispatch.ps1 -Task T5 -Model gpt-6.1-sol -Worktree [-From task/T4]`,在后台运行,再 `progress.py set-status T5 doing`。途中不监视。
- 脚本是监工:缺最终报告就要求补,阶段证据不全又没停下就续"继续"。结束后脚本在任务分支提交改动、记台账,报告存为 `dispatch-logs/evidence/T5/report.md`。
- 助手停下时,回答它:`-Resume 会话编号 -Message "……"`。回答改变契约时加 `-Contract`,脚本先写进简报"已定"。产品问题 spec 里没有答案,先问 Lily。
- 续用还是新开,看上下文:助手会话已经很大时,新开会话,交给它 diff、报告和回答。M2 实测:大会话续用 1 次比新开贵。

## 审查与修改
1. `codex-dispatch.ps1 -Task T5 -Model 模型名 -Review [-Resume 审查者的会话编号]`,脚本先把 main 合并进任务分支。可选:同一份 diff 再交给 sonnet 子代理审一次,对照两边的发现。
2. 记结论:`ledger.py review --task T5 --result pass 或 changes --findings 条数`,它同时改进度。
3. 要改的,合成一次批量修改请求交给助手,修完再审。连续 2 次"审查通过、试玩却有 bug",换新的审查会话。
4. 代码问题都修好、只剩人工验收时,lead 可以加 `--by lead --note "复审了哪些"` 记 pass。

## 接手
出现任意 1 条,lead 处理,并运行 `ledger.py flag --task T5 --flag 接手 --signal 信号`:
| 信号 | 情况 |
|---|---|
| 测试修2次 | 同一个测试修了 2 次仍失败 |
| 超预估 | 时间或 token 超过简报预估的 2 倍 |
| 同类意见2次 | 同一类审查意见出现 2 次 |
| 要改验收 | 助手要求改测试或验收标准来通过 |

处理顺序:先把简报降 1 级;仍不行换更强的模型;最后 lead 自己做。

## 合并与收尾
1. `codex-dispatch.ps1 -Task T5 -Merge`:检查审查结论和两边目录、把 main 合并进任务分支、跑测试存证据,通过才合并进 main 并改状态。要 Lily 试玩的加 `-Playtest`。
2. 试玩 bug:`ledger.py bug --task T5 [--count 2]`。合并后:`-Cleanup` 先保存证据,再删工作目录和分支。
3. 里程碑开始和结束时,用 Claude 应用的用量工具读 lead 会话的 token,运行 `ledger.py lead`。不让脚本读 Claude 的记录。
4. 里程碑结束:按 LiEC 的收尾做。lead 会话按里程碑换新的。

## 提交
- lead 自己的提交:Agent 写 `Claude Code`,Model 写当前模型,Session 写当前会话编号。按模型查提交:`git log --grep "Model: gpt-6.1-sol"`。
- 一个简报的会话中途不换模型。便宜的模型不一定省钱,返工也算开销。
