# lyfusion 迭代建议:改为边界交接,做一次减法

> 写的人:CraftTax 的 lead(Claude Opus 5.5,会话 f1175d14)。Lily 2026-11-02 同意方向,让我把这一轮的结果、结论和思路交给你。
> 取代 `2026-10-29-fusion-v4-draft.md`(那份想复杂了,请不要按它落地)。M2 数据见 `2026-10-29-m2-retrospective.md`。
> 这份是建议,不是定稿。哪些落地、怎么落地,由你和 Lily 定。

## 一、结论(Lily 已同意方向)
1. **通信改为边界交接**,按 Cognition Fusion 原文的图 1:探索(返回文件片段)→ 计划 → 助手一口气执行完 → 交回最终报告和 diff → lead 审查 → 一次批量修改请求 → 助手修复 → 合并。中途不通信。
2. **交换产物,不交换叙述。** 片段、计划、diff、修改请求本身就是事实;阶段回报、状态消息只是事实的副本,也是文书的来源。
3. **助手遇到停止条件,就结束本次运行**,把问题写在最终报告里;lead 回答后续用会话(或在上下文已很大时,开新会话,交给它 diff 和回答)。
4. **做一次减法。** 每个机制写明它补偿哪种能力不足、那个不足还在不在;不在的删掉。

## 二、为什么:M2 的证据
| 观察 | 数据 |
|---|---|
| lead 是最大的开销 | M2 期间 lead 238 次调用,缓存读取 5,714 万;T11 的 Codex 全部运行合计 3,092 万 |
| 贵的是重读,不是消息 | 一条消息约 1 千 token;lead 每次调用平均重读约 24 万上下文 |
| 实时信箱几乎没传有用的东西 | T11 的 7 次阶段回报加 7 次阶段审查,审查全是 ok;2 次提问是简报歧义和一个本该在计划里定的接口 |
| 并行不需要途中通信 | T12 用占位方法代替 T11 的接口,合并时 lead 改 1 行就接上 |
| 会话连续 ≠ 省上下文 | M1:续用 2 轮的旧会话 244 万,新会话 106 万。M2:T11 修审查意见续用 1 次 1,367 万,比 34 分钟开发(921 万)还多 |
| lead 的调用多是文书 | 262 次工具调用里文书类约 42%,改代码 4 次 |

## 三、迭代史的复盘(Lily 和 lead 一起得出)
- **v1 停下的病根是决策权和简报,不是"会话被中断"。** M1 的停顿来自:权限太窄(改一行注册也算越界)、环境问题、简报不清、按角色拆分(3 行修复走 5 个会话)。
- **信箱是治症状的补丁。** 它解决"停了以后怎么办",没解决"为什么会停"。病根后来由第 3 轮的决策权分级、环境脚本、简报模板治好了。两种改动同时上线,分不清谁起作用,补丁就留了下来。
- **只测助手,成本挪到 lead 没被看见。** 台账只记助手的 token。先测整个系统,再优化局部。
- **脚手架要能拆。** 每个机制补偿某种能力不足;模型变强后(gpt-6.1-sol、Opus 5.5),有些补偿变成负担。M2 的 7 次阶段审查全是 ok 就是信号。
- **一次只改一个主要变量**,并事先写预测。第 2、3 轮同时改了通信方式和决策权,所以无法归因。

## 四、两个独立 Opus 会话的方案(Lily 要求的对照)
做法:开 2 个 Opus 5.5(medium)新会话,只给 CraftTax 的事实和约束,不给我们的框架,问它们会怎样调度 M3。原文在会话 local_553ec17f 和 local_20c4e42f。

**两份独立得出、和我们一致的:**
- 只在任务边界交换,载体是文件:派工单 → 最终报告(固定段落,不超过 60 行)。中途卡住就写进报告、结束本轮,续用时带上回复。
- 跨模块接口由 lead 在实现前定死。
- lead 只读报告和 `git diff --stat`,长日志交给 haiku 摘要,不读助手的完整过程。
- lead 上下文到约 15 万,或一个阶段结束,就写一份短状态文件,换新会话。
- 写代码的助手同时不超过 2 个;不搭消息总线、不做自动循环、不做插件框架;数值放配置表,Lily 自己能调。

**值得吸纳的新东西:**
1. **接口写成可编译的 Java 存根**(接口加空实现,先提交 main),而不只是 `interfaces.md` 里的文字。下游用存根和假数据先开工。这把 T12 的"占位方法"变成了标准做法。
2. **按助手强弱,定接口的深度不同:** 强助手只给签名和不变式(如"点数不为负""概率夹在 0 到 1");弱助手给代码骨架和会失败的测试,甚至写死文件位置和样板。
3. **审查交给一次性的 sonnet 子代理**,只带 diff 和接口文档,返回按严重程度排序、最多 10 条的清单;lead 只深读有疑问的几处。和现在的 Codex 审查者相比,值得做一次对照:Claude 审 Codex 的代码,模型来源也不同。
4. 要改别人的接口时,先在自己模块里做一层适配绕过去,在报告里提修改请求(A 的做法),不停下。

**两份都没有、我们自己的:**
- **lead 自身的 token 实测。** 两份都估 lead 整个 M3 只要 12.5 万~50 万 token,这是按"上下文大小"估的。实际费用是"上下文 × 调用次数":M2 实测 5,714 万。模型(包括测量之前的我)都会犯这个口径错误。建议 lyfusion 写明成本模型。
- **品味层。** 两份都把手感和画面只交给 Lily 的试玩清单,界面"先用原版风格"。谁负责"好不好玩、好不好看",两份都没回答。
- **一处和我们的数据冲突:** B 说"后端连续任务续用同一个 Codex 会话,省掉重新读代码"。我们的数据是上下文大了以后,续用比新开贵。建议规则写成按上下文大小决定,而不是固定续用。

## 五、Lily 的问题:接口交给 lead 还是助手定
**看谁在用这个接口,不看级别:**
| 情况 | 谁定 |
|---|---|
| 并行任务要用另一方的接口 | lead 在派工前定死,写成可编译存根 |
| 只有后面的任务才用 | 助手定,写进最终报告;lead 审 diff 时确认 |
| 模块内部的类和方法 | 助手定(L2、L3) |

**级别决定定到多深:** L1 写到存根加失败测试;L2 写跨模块签名;L3 写契约内容和不变式,签名可以由助手在"探索"那一步起草,lead 拍板。两个独立会话都同意:lead 最值得花算力的地方,就是开头把接口定准。

## 六、减法清单(对照 lyfusion 现有机制)
| 机制 | 补偿什么不足 | 现在 | 建议 |
|---|---|---|---|
| 实时信箱(`inbox` 每阶段读、`wait`、`watch --follow`、Monitor 监视) | 助手一有问题就结束会话 | 病根已由决策权治好;M2 几乎没传有用信息 | **删**。改为最终报告和续用时的回复 |
| 阶段回报消息(`mail.py send report`) | lead 要早点发现跑偏 | 7/7 阶段审查是 ok | **删消息**。阶段留作助手的内部结构,证据照样存目录 |
| lead 逐阶段审查 | 助手容易跑偏 | 同上;问题都由模块审查发现,修得很快 | **删默认**。简报可标 1 个"检查点"阶段(高风险时),做完停一次 |
| `reply --contract` 写进简报"已定" | 决定要留在简报里 | 仍需要 | **保留功能**,改挂在续用时的回复上(或并入 `brief.py`) |
| 派工脚本监工(缺阶段续"继续",缺回报续"补回报") | Codex 中途提前结束 | 仍可能发生;不花 Claude | **保留**,"补回报"改成"缺最终报告就补" |
| 最终报告 schema(`final.schema.json`) | 报告格式不一 | 正是边界交接需要的 | **保留并加强**:固定段落,加"假设""接口修改请求",不超过 60 行 |
| 台账(从信箱算一次通过、已答提问、lead 消息) | 看不到各模型表现 | 信箱删后这些指标失去来源 | **改**:记每次运行的 token、审查发现数、试玩 bug,**加 lead 的 token**(lead 用应用的用量接口读,不让脚本读 Claude 记录) |
| 自主级别 L1~L3 及升降级 | 模型能力有差异 | 仍需要 | **保留**,加上第五节"定接口的深度" |
| 简报模板与 `brief.py check` | 简报歧义 | 仍需要;M2 仍有 1 次歧义 | **保留**,加"接口存根路径"和"报告格式" |
| 接手信号表 | 助手能力不够要换人 | 仍需要 | **保留**,删掉依赖信箱的信号 |
| 前端归属规则 | 后端模型做不好美术 | 仍需要 | **保留**,另加品味层(见下) |
| 提交钩子(5 行追溯) | 追溯谁写的 | 自动、几乎零成本 | **保留** |
| 环境预检、PATH、复制授权文件 | 环境问题让助手停下 | 已证实有效(M2 环境提问 0) | **保留** |
| Codex 模块审查(`-Review`,先合并 main) | 实现者自查不够 | 仍需要 | **保留**,并对照试一次 sonnet 子代理审查 |
| `-Cleanup`、证据目录 | 证据丢失 | 仍需要 | **保留** |

**建议新增(每项都要删掉 lead 的一类手工步骤,否则不加):**
- 接口存根:派工前提交可编译的存根和不变式。删掉:并行任务的途中通信。
- 一条"合并任务"命令:检查主目录、合并、跑测试、存带抬头的证据、改状态,有冲突就停。删掉:lead 合并时的十几步。M2 我两次因为手工步骤出错(没提交主目录、漏带参数)。
- lead 会话按里程碑,换会话时由脚本生成短状态文件。删掉:lead 在 26 万上下文里继续干活。
- 长日志、长报告先由 haiku 压成摘要。删掉:lead 读原始材料。

**品味层(Lily 2026-11-02 定:放 LiEC,单 agent 项目也能用):** 每个里程碑写 3~5 条体验目标;拆任务前 lead 做设计稿和 Lily 定稿;前端证据要截图,lead 做设计评审;打两个分(交付分、作品分)。M2 的打分理由全是流程指标,这是信号。

## 七、建议在 CraftTax M3 验证的预测
| 预测 | M2 基线 |
|---|---|
| lead 每个任务的缓存读取 ≤ 950 万 | 约 2,860 万 |
| lead 工具调用里文书类 ≤ 30% | 约 42% |
| 途中通信(助手和 lead 之间,停止条件除外)= 0 | T11 20 条信箱消息 |
| 交付分 ≥ 4,作品分 ≥ 4 | 交付分 4,作品分没打 |
| 环境类提问 0,问 Lily 的次数不增加 | 0 |

只换一个主要变量:通信方式。M3 只是 1 个里程碑,预测落空或成立都只当线索。**最强的反对意见:** 对 CraftTax 的规模,单 agent 加好的测试也许就够了;如果边界交接的预测仍然落空,下一步应试"单 agent + 脚本",而不是再加结构。
