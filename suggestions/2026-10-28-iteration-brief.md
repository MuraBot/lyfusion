## 一、Lily 的想法

### 核心判断(按讨论顺序)
1. 协作 agent 自己做验收,调度者不做杂活。验收命令(构建、运行服务器和客户端)由写代码的 agent 运行。
2. 架构要模块化、数据驱动:一个类只做一件事,可调内容放数据文件。
3. 每一轮派工都记录可优化点,分 3 类:〔传递〕agent 间的信息传递、〔自主〕agent 的自主权、〔阻塞〕流程的阻塞。
4. 截图、帧率这类人工验收,执行者要在拆任务时定好(这次由 Lily 自己测)。
5. 工作流"有些奇怪":lead 的规划能力被用在文书工作上。Lily 认为这是她的安排失误。
6. 想参考 Devin Fusion:强模型当 lead,负责计划、解释歧义、审查;sidekick 有自主权;双方各自有持久的上下文。
7. 关键问题是 2~4 个 agent 之间怎么高效传递信息:规划和美术由 Claude 做,后端和审查由 Codex 做。
8. 能用程序保证的协议,不靠模型自觉。
9. "尽早能玩"可以推广到其他项目,叫"尽早能用"。

### Lily 提出的 7 个深层问题(草案第四至第九节在回答)
1. 助手怎样不结束会话就能问 lead,并等待回复?简报有没有不随 lead 模型变化的写作标准?
2. 拆分阶段有没有标准或提示词?现在全靠模型自己理解。
3. 怎样让助手一口气做完 1~10,而不是做完 1 就停下回报?
4. 简报、结果、反馈怎么适配长会话?
5. lead 什么时候审查 diff?问题怎么不打断地告诉助手(类似 Codex 的"指引")?什么时候由 lead 接手?
6. 简报写多细?怎么量化模型能力和简报的"指导性"?
7. 是否鼓励强的助手提异议?弱的助手固执己见会增加成本。

### Lily 已经做的决定
- 按模块和上下文拆分,不按角色拆分。后端编写和审查各用 1 个 Codex 长会话,上下文按模型自带的方式压缩。
- 后端会话自己写测试。测试只测用户能感知的行为。
- 独立性只放在 2 个点:开工前的接口和验收标准,模块合并时的审查。
- 调度者的文书工作交给脚本。
- Q1:助手可以在自己的任务分支上按阶段提交,不推送,不碰 main。
- Q2:文件信箱加 lead 在 Lily 开着的对话里监视,不算 Codex 调用 Claude,也不算无人值守。
- Q3:提问超时后,可撤回的决定按保守假设继续;产品决定或不可撤回的操作,先做别的阶段。
- Q4:gpt-6.1-sol 从 L3 起步,其他新模型从 L2 起步。
- L3 遇到产品决定或接口变更可以不停下,细分见草案第六节。
- 冒烟检查改为可选,执行者按开销选:haiku、gpt-6.1-terra、Lily 或 lead。
- 提问等待时间暂定 10 分钟。
- 前端可以由后端模型全权负责。判断条件见草案第四之二节。
- 审查者长会话先不换。lead 审每个阶段的 diff,审查者审模块合并。
- 自动试玩截图对比只记为候选。
- 本次迭代由 skill 会话负责,CraftTax 会话用 M1 剩下的工作试点。

## 三、命令测试结果
- 测试时间:2026-10-28。codex-cli 0.164.0-alpha.11.1。
- `codex exec --help` 列出了 `--output-schema <FILE>` 和 `-o, --output-last-message <FILE>`。
- 实测:gpt-6.1-sol low,只读沙箱,给一个 3 字段的 JSON Schema(类型、阶段、摘要)。
- 实测:最后一条消息写进 `-o` 指定的文件,内容是 `{"type":"回报","phase":1,"summary":"阶段 1 已完成。"}`。
- 结论:`--output-schema` 可用,草案第十节可以用它约束最后一条消息。
- 注意:Schema 要写 `additionalProperties: false`,并把字段都列进 `required`。
- 注意:Codex 的可执行文件不在 PATH 里。派工脚本从 Windows 应用包里找 `codex.exe`,新工具要复用这段逻辑。
- 注意:这次测试共用 20,508 token,但跑了 3 分钟以上。日志有 2 次"刷新模型列表超时"。`mail.py wait` 和监工的超时要把启动耗时算进去。
