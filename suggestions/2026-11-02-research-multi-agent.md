# 调研笔记:多 agent 协作与类似 fusion 的做法(2026-11-02)

> 来源:3 个 haiku 子代理(2 个查 arxiv,1 个查 GitHub)的摘要;下面标"已读"的,lead 亲自打开 arxiv 摘要页或正文核实过。只是建议,还没有改任何规则。

## 一、和小熊对比实验直接相关的发现

| 论文 | 核实 | 发现 | 对照我们 |
|---|---|---|---|
| [AgentCARD](https://arxiv.org/abs/2606.20629)(2026-05) | 已读结论 | 异构队伍(规划者和执行者用不同模型)占据花费-准确率前沿,最多 +44%,或以 1/12 花费追平最强同构队伍。**执行者读的输入是规划者的 200 倍,每任务花费中位数是规划者的 6 倍**。瓶颈角色看领域:有的领域卡在规划者,有的卡在执行者 | 我们反过来:lead 占 77~97%。说明我们的 lead 不只在"规划",还在反复读大上下文、看截图、改方向,干了执行者和审查者的活 |
| [Can Small Agents Collaborate…](https://arxiv.org/abs/2601.11327)(2026-01) | 已读正文 | 系统表现主要取决于调度者(orchestrator)的能力,不是子 agent 的大小。调度者开思考收益最大;子 agent 开思考收益很小甚至为负,还加 77% 延迟。调度者每轮只留**紧凑摘要**而不是整段历史,token 少 43% | luna 开 max 思考没换来效果。lead 每轮重读全部历史,是花费大头 |
| [Tokenomics](https://arxiv.org/abs/2601.14470)(2026-01) | 已读摘要 | ChatDev 30 个任务:迭代的代码审查阶段占 59.4% token,输入 token 占 53.9%。花费主要在精修和验证,不在第一次生成 | 和我们一样:改了几轮反而贵、反而差 |
| [Adversarial Review](https://arxiv.org/abs/2608.18167)(2026-08) | 已读摘要 | 主 agent + 审查者 + 批评者三个 agent 胜过五 agent 基线。朴素的审查会"假共识":没有足够证据就达成一致。要求显式、结构化、**有证据**的分歧后最好 | lead 的建议"听起来对、改完变差":建议没有经过对照证据(初版截图 vs 改后截图)的检验 |
| [PEAR](https://arxiv.org/abs/2510.07505)(2025-10) | 已读摘要 | 弱规划者比弱执行者更拖累整体;规划者需要记忆模块,执行者不需要 | 支持"lead 用强模型";但不解释 lead 为什么那么贵 |
| [SPOQ](https://arxiv.org/abs/2606.03115)(2026-06) | 已读摘要 | Opus 工作者、Sonnet 审查者、Haiku 调查者三层;执行前查计划、执行后查代码两道关,缺陷 0.34→0.20;人工审查把残留缺陷 0.47→0.03 | 和 LiEC 的"简报检查 + 证据检查 + Lily 试玩"同构;人的一眼最值钱 |
| [Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/abs/2503.13657)(2025-03) | 子代理核实 | 1600+ 条轨迹,14 种失败模式,三类:系统设计、agent 间不对齐、任务验证。多 agent 在常见基准上收益往往很小 | 可以拿它的分类给我们的 `flag` 记录打标签 |
| [AI Agents That Matter](https://arxiv.org/abs/2407.01502)(2024-07) | 子代理核实 | 只看准确率会误导,要同时报花费、画帕累托前沿;简单基线常能追平复杂 agent | 正是帕累托查看器的思路;单 agent 应该一直当对照基线 |

## 二、GitHub 上的类似项目

- [Bernstein](https://github.com/sipyourdrink-ltd/bernstein)(已读 README,beta、一人维护,星数未查到):"治理层"。调度是纯 Python,**协调环节不用模型**;每个任务一个 worktree,过合并关卡才合并;每一步都有可回放的记录。理念和 lyfusion 的派工脚本最像,但体量大得多,适合参考,不适合直接换。
- [claude-squad](https://github.com/smtg-ai/claude-squad)(子代理报 8.7k 星,AGPL-3.0):tmux + worktree 并行管理多个 Claude Code / Codex,只管隔离,不管调度、审查、记账。
- [agent-orchestrator](https://github.com/OrchestratorInc/agent-orchestrator)(子代理报 14k 星,未核实):每任务一个 agent、分支和 worktree,审查 agent 把 CI 失败回派给对应 worker。
- [Aider](https://github.com/Aider-AI/aider) architect/editor 模式:强模型出方案、便宜模型落文件,单工具内两模型分工。
- 没找到"把多个模型的结果融合"的编程项目;FuseLLM 是训练层的融合,无关。

## 三、给 lyfusion 的启发(按把握从高到低)

1. **lead 的花费结构是反的,这是首要问题。**文献里贵的是执行者,规划者只读少量输入。可以考虑:lead 每个里程碑只读简报、最终报告和截图,不读整段历史;长会话按里程碑换新会话,用进度文件交接(相当于论文里的"紧凑摘要")。
2. **lead 的修改建议要过证据关。**改之前把"初版"截图留作对照,改完并排比较;改差了就回退。对应"有证据的分歧",也对应小熊腿的问题。
3. **助手不必开最高思考档。**思考放在调度者身上收益最大,子 agent 开 max 收益小、更慢。
4. **单 agent 永远是对照基线**,帕累托查看器里要一直有它;小任务直接单 agent。
5. 只有在任务大到能并行、或者执行量远大于规划量时,lead + 助手才可能划算。小熊这种单页面任务本来就不在这个区间。

## 四、局限

- 多数论文的任务是问答、数学、检索,不是创作或前端;"Can Small Agents" 用的是 8B/32B 开源模型。
- 没找到"指令详细程度"和"批评让质量变差"的直接研究。
- GitHub 星数大多来自子代理抓取页面,只有 Bernstein 是我亲自看的。
