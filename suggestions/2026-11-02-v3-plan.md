# lyfusion v3 迭代方案:轻 lead(草案,2026-11-02)

> 依据:`2026-11-02-research-fusion-gap.md`(Cognition Fusion、AA 榜单、Anthropic advisor、12 篇论文)和小熊对比实验。
> 状态:Lily 已定第六节的 4 个决定,下一步是 M0。还没改任何规则或代码。

## 一、目标先说清楚

Lily 的目标:达到 Devin Fusion 80% 的效果。
- 在 AA 榜单上,Fusion(Opus 5.5 + Luna)68.1,Opus 单 agent 66.0。**单用 Opus 就已经有 Fusion 97% 的效果**。所以只看质量,最省事的答案是"不用 lyfusion"。
- Fusion 的价值是**同样的效果、更少的花费**(−31%)。对 Lily 来说,花费就是两个订阅的额度,其中 Claude 的额度最紧(lead 用的就是它)。

所以建议的目标(待 Lily 确认):
| | 及格线 | 理想线(≈ Fusion) |
|---|---|---|
| 质量(测试通过 + Lily 打分) | ≥ Opus 单 agent 的 80% | ≥ 95% |
| Claude 用量(每任务) | ≤ Opus 单 agent | ≤ 70% |
| 时间 | ≤ 单 agent 的 2 倍 | ≤ 1.3 倍 |

## 二、新架构:两种模式 + 两条铁律

**人数(Lily 2026-11-02):1 个 Claude lead + 1 个 Codex 助手;前端需要时最多再开 1 个 Claude 子代理,或者 lead 自己做。不开审查者。**

lead 接到任务先花 1 分钟判断模式(相当于 Fusion 的路由):

| 模式 | 什么时候用 | 谁写代码 |
|---|---|---|
| **独做** | 短任务(lead 预计 10 轮内做完);判断就是交付物(审美、交互意图);连续排错 | lead 自己 |
| **搭档** | 能拆出执行部分:实现 + 跑测试、机械改动、迁移、测试很慢 | Codex 助手 |

**铁律:同一时刻只有一个 agent 在写同一个分支。**并行只在模块完全不相干时用(Cognition、Factory 都得出"串行加有针对性的并行"更好)。

### 搭档模式的 lead 守则(取代 dispatch.md 的大部分)
1. **早放手**:第 1 次交接越早越好。助手强(sol),第一步可以就是"探索并汇报文件路径和片段,先别改";助手弱(luna),lead 自己快速探索(几次读取),再交出去。
2. **简报是规格,不是口述**:目标、约束和不变式、边界情况、"做完"的定义(命令 + 期望结果)、要汇报什么。不写代码,不贴整个文件。
3. **按助手强弱调简报**(取代 L1~L3 的通用规则):
   - 弱助手:写得具体(步骤、涉及的文件),不让它反驳方向,规划用的探索不交给它。
   - 强助手:写目标和约束,允许它在最终报告里反驳简报("简报可能错了,因为……")。
4. **lead 只读三样**:最终报告、`git diff --stat`、关键改动片段(`git show`)。不重读助手已经汇报过的文件。
5. **审查意见变成新的交接,lead 不亲手改**:"先试更简单的写法,保留第一个能通过的"。只有出现接手信号时 lead 才自己动手。
6. **助手会话常驻**:同一个任务的后续交接都续用同一个 Codex 会话(保留它的上下文)。每个任务目标 ≤ 3 次交接。
7. **lead 的轮数预算**:每个任务 ≤ 15 轮。超了就记 `flag`,复盘看是哪一类动作占的。

### 不设审查者(Lily 2026-11-02)
- 审查只由 lead 做:看 diff 和测试。弱助手审强模型的代码,意见还得 lead 逐条判断和反驳,反而加重 lead(Cognition 也发现弱助手不该被鼓励提意见)。派工脚本的 `-Review` 和审查者角色删掉。
- 审美类意见必须附"改前/改后"截图,改差就回退。

### lead 本身减重
- 测 lead 会话的开场上下文(小熊实验约 10 万)。目标 < 4 万:lead 会话只加载 lyfusion 的精简说明,执行期间不读 LiEC 的阶段文档;按里程碑换新会话,用进度文件交接。
- 文书自动化:派工脚本顺手做 `progress.py set-status` 和台账记录,lead 每次交接只运行 1 条命令。

每个任务记:自动检查分、Lily 打分(只给有判断的任务)、Claude 用量(开场/结束上下文 + 轮数,换算成估算花费;或 5 小时额度的百分比)、Codex 用量(台账)、时间。帕累托查看器已经能画。

## 五、要不要开 loop 做"调研-优化-测试"

我的建议:**现在不开。M2 调参时可以开一个有上限的。**
- 每一轮测试都要真跑 Claude 和 Codex,消耗两个订阅的额度。无人看着的 loop 可能一下子把 5 小时额度用光。
- fusion-bench 里有判断类任务,要 Lily 打分。loop 只能看自动检查分,容易往"能测的"方向跑偏。只有 6 个任务,轮数一多就会对这 6 题过拟合。
- 架构改动(M1)每一步都需要判断,适合我们一起做。M2 是"改一个参数、跑一遍、看帕累托点",最适合 loop:限定轮数(例如 4 轮)、只跑有自动检查的任务、每轮只改一个变量,Lily 在场时开。
- 调研本身也不需要 loop:这次 4 个子代理加细读 15 分钟就做完了,下次需要时同样做法就行。

## 六、Lily 的决定(2026-11-02)

1. **目标口径**:质量 ≥ Opus 单 agent 的 80%,且每任务 Claude 用量低于单 agent。
2. **测试任务**:自造的小仓库,**由 Codex 出题**,避免出题人就是做题人。先不从 CraftTax 挑真实任务。
   - lead 补充的防偏措施:出题用不参加任何测试配置的 gpt-6-astra,推理档 medium(Lily:high 太贵);隐藏测试和评分脚本放在做题仓库之外,做题的 agent 看不到;Claude 只负责检查题目能不能跑,不改题意。
3. **搭档模式的配置**:lead 用 Opus 5.5 high,助手用 gpt-6-luna max。借这组探索"简报到底要多具体"。
   - 因此 M1 里加一个小实验:同一批任务给 luna 两档简报(具体档:步骤和涉及的文件;规格档:约束和"做完"的定义),比质量和 lead 用量。
   - sol high(Lily 日常单 Codex 开发用的)放到 M2 和 luna 比较,推理档也在 M2 比。
4. **loop**:M2 调参时再开有上限的(限轮数、只跑自动检查的任务、每轮改一个变量、Lily 在场)。
