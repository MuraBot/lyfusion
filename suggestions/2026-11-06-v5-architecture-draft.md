> HEX 通信诊断(`2026-11-05-hex-communication-diagnosis.md`)、插件调研(`2026-11-06-plugin-research.md`)。

## 1. Lily 想要的(我的理解)
- 头号目标是**质量和优雅**,不是省 Claude 用量。用量省下来是顺带的结果
- **把规则升级成程序**:不靠文字提醒,靠工具和检查保证
- **选了 Fusion 就等于开始 lyfusion**:分别选 lead 和助手的模型、推理强度、快速档,不用每次口头交代
- 要解决的根本问题:长任务里 lead 对设计的把控会丢。HEX 出现过,Devin 的 Fusion(Opus 5.5 + SWE-2)也出现过
- 版本范围:一个"能用的插件",不是最小版,也不是最大版
- 派工脚本不是非保留不可,看实现

## 2. Devin Fusion 博客里的要点
1. **两个并行的完整代理**,各有自己的工具和**各自的缓存上下文**。比"顾问工具"好,是因为每次问顾问都要重新付一遍上下文的钱,而常驻的助手不用
2. 主代理**默认只委派和监控**,自己只做重大决定:计划、对歧义的解释、最终审查。动作尽量少,只读绝对必要的东西
3. **动态路由**:用轻量分类器判断该谁来主导。在上下文压缩时顺便切换模型,因为压缩本来就会让缓存失效,等于免费换模型
4. 博客里的五个例子(都是对比 Devin 单独做):
   - 慢测试交给助手:花费 -62%,分数 +2
   - 跨多文件的机械删除:-32%,分数 -1
   - 难但机械的集成(复用上游代码):-25%,分数 **+12**
   - **难的、多文件的 React 功能,考的是判断**:-28%,分数 **-27**。博客原话的意思是:判断本身就是交付物时,委派会适得其反
5. 路由示例(Lily 截图的那个)按时间顺序:
   - 前沿模型 1:初始化环境、读知识笔记、定位代码
   - 便宜模型:切分支、读文件、分析两个 API。这些"只是读",不需要前沿智能
   - 前沿模型 2(另一个前沿模型,更适合实现):定计划;四项改动和 lint、类型检查都委派给助手;自己审查助手的改动并开 PR
   - 便宜模型:回复审查机器人的意见、盯 CI、看构建结果
   - 也就是说:"谁主导"会随阶段换人,主导者再把杂活派给助手。截图里"Frontier Model 2"指的就是第二个前沿模型,"its own cached context"是说助手一直用同一段会话,不用重新读代码

## 3. 回看 v4:哪些做到了,哪些没做到
| Cognition 的原则 | v4 的情况 |
|---|---|
| 两个代理并行 | 没有。lead 派工后基本在等;问题攒到最后才在报告里出现(HEX 的分支问题问了 3 次都没人回答) |
| 各自的工具集 | 没有。lead 什么都能做;"前端归 lead"是一句文字规定,对其他工作也没有划分 |
| 各自的缓存上下文 | 有,但没有边界:HEX 一个 Codex 会话从 T2 用到 T12,1.52 亿 token,报告和修改请求都受了污染 |
| 主代理少动作、少读 | 部分做到(探索包、交接包);但"该读什么"还是 lead 自己判断 |
| 重大决定归主代理 | 计划写多细没有标准;成功标准自相矛盾(T4 把 T2 的数值测试改弱了) |
| 判断性的工作不委派 | 只有"前端归 lead"一条,对其他的判断性工作没有覆盖 |
| 按信号切换主导者 | 没有 |

## 4. v5 的核心想法

### 4.1 按"判断在哪"分工,而不是按"前端还是后端"
每项工作在计划里标一个类型:
| 类型 | 例子 | 谁做 |
|---|---|---|
| 判断 | 用户能感知的设计、交互和数值;模块之间的接口和数据格式;对歧义的取舍 | **lead 自己做**,或者写成不留余地的决定 |
| 机械 | 按已定接口实现、迁移、重构、删除、补测试 | 助手 |
| 验证 | 跑慢测试、lint、类型检查、盯 CI | 助手(永远) |
| 探索 | 读代码、查 API、找出相关文件 | 助手 |

这是对 Devin -27 分那个例子的直接回应,也是"长任务里设计把控会丢"的主要解法。

### 4.2 计划要"决定完整",不要"步骤完整"
- 判断标准:**两个能干的工程师照这份计划各做一遍,用户分不出差别吗?** 分得出来,就说明还缺一个决定
- 计划写决定、接口、验收检查;不写实现步骤(那是助手的事)
- 这也回答了"许愿式开发不适合某些模型":给助手的永远是决定,不是愿望

### 4.3 意图记录(长任务把控的关键)
- 项目里有一份 lead 维护的 `fusion/intent.md`,记录已定的设计决定:编号、内容、理由
- 每个任务都引用相关的决定编号;助手的报告要写明每个决定是怎么实现的、哪里偏离了
- 长任务里新会话(无论 lead 还是助手)先读这份记录,而不是靠聊天历史
- 偏离由程序列出来,lead 只看被列出的部分

### 4.4 交接用有格式的数据,由程序检查
- 任务单和报告都用 JSON 格式(v4 的报告已经是),派工工具会拒收不合格的任务单:没有验收检查、没有文件范围、引用了不存在的决定编号
- 验收检查由程序去跑,不信助手自己说的"测过了"
- 文件范围、禁止操作、删弱测试这些 v4.2 已有的检查保留,并从"事后报告"改成"当场拦下"

### 4.5 两个代理并行,问题随时冒出来
- 助手在后台跑,lead 同时做自己的判断性工作
- 助手一有问题就立刻通知 lead(monitor 或 mod),lead 回答后直接送回正在跑的助手(Codex 有 `codex queue --thread --message`)
- 同一时间同一个文件只归一方:助手负责的文件,lead 改的时候被程序拦下;反过来也一样

### 4.6 什么时候换人(用信号,不用分类器)
用确定的信号代替 Cognition 的分类器,符合"用成熟、无聊的技术":
- 助手在同一项验收检查上连续失败 2 次 → 提醒 lead 考虑接管
- 助手提出的问题涉及意图或设计 → 必须由 lead 回答
- 助手的改动碰到了标为"判断"的文件 → 拦下,交 lead 决定
- 助手会话超过阈值(比如 3000 万 token)→ 写交接摘要,换新会话(对应 Cognition 的"压缩时切换")
信号由程序发出,决定仍由 lead 做。

### 4.7 lead 只读必要的东西
程序把交接整理成三层,lead 默认只看第一层:
1. 验收检查结果、偏离意图记录的地方、助手的问题
2. 判断类文件的改动、被检查或复审标出来的改动
3. 完整 diff 和日志(只在需要时看)
可选:在 lead 审查前,先让 Codex 用 `codex review` 对照意图记录复审一遍(对应 Devin Review)。

## 5. 插件里怎么落地
| 想法 | 插件组件 |
|---|---|
| 选 Fusion = 开始 lyfusion | mod:`/fusion` 开关;输入框上方画一条 Fusion 栏,显示和选择助手的模型、推理强度、快速档。lead 的模型就是会话本身的模型(用 Claude Code 自带的选择器)。设置存在项目文件夹里。**原生模型选择器不是 mod 能改的地方,所以做不到在里面加一个"Fusion"选项** |
| 开着 Fusion 时自动进入 lead 角色 | 钩子在会话开始和每次提问时注入 lead 的说明和当前任务状态 |
| 各自的工具集 | lead 的工具:`fusion_delegate`、`fusion_answer`、`fusion_review`、`fusion_accept`、`fusion_takeover`(mod 注册的工具或 MCP 工具);对助手负责的文件,mod 拦下 lead 的 Edit 和 Write |
| 助手常驻并行 | 后台跑 Codex(`exec --json` + `resume` + `queue`,或者实验性的 `app-server` 守护进程),monitor 把事件转成给 lead 的通知 |
| 任务单和报告的格式检查 | 工具的参数结构 + 程序校验 |
| 面板 | 显示任务、意图记录的引用、助手进度、待回答的问题 |

动态切换 Claude 模型:mod 的 `turn.step` 可以把某次请求换成别的模型。但 Lily 不追求省用量,而且中途切换会让缓存失效,所以 5.0 先不做。

## 6. 5.0.0-a 做什么、不做什么(待定)
**做**:Fusion 开关和设置栏;lead 和助手的工具;任务单和报告的格式与校验;意图记录;助手后台跑、随时提问;文件归属拦截;换人信号;三层交接;在 fusion-bench L1 上和 v4.2、Opus 单独做比较。
**不做**:Claude 模型的动态路由;自己的市场和上架(先用本地文件夹加载);LiEC 集成;多助手。

## 7. 要先试一试的

- mod 的 `$.process.spawn` 在 Windows 上长时间跑 Codex 稳不稳
- mod 拦截 Edit/Write 时,能不能按文件路径区分

## 9. 架构大改的提议
1. **一条事件流做唯一的数据来源。** 项目里只有一个只追加的 `fusion/journal.jsonl`,记录所有事件:建任务、派工、助手提问、回答、检查结果、审查意见、验收、用量。台账、交接、面板、任务状态都从它算出来。现在的台账、进度、证据文件夹、`bundle-prev.md` 各存一份,容易对不上。
2. **引擎和外壳分开。** 引擎(`fusion-core`)只管助手、检查和事件流,不知道 Claude Code 的存在,可以用假 Codex 测试,以后也能直接拿去跑基准测试。外壳是插件:Fusion 栏、面板、工具注册、拦截、钩子。外壳调用引擎。
3. **助手是有生命周期的"工位"。** 每条工作线一个常驻助手:启动、接上、换新、关闭都由引擎管,lead 只说"派给助手"。
4. **lead 不再拼命令行。** lyfusion 的操作全部是带参数结构的工具,参数不对当场报错。
5. **意图记录用数据存。** `fusion/intent.json` 是数据,同时生成一份给人看的 Markdown;工具可以校验"引用的决定编号存不存在"。
6. **每项工作是一个状态机。** 已提出 → 判断类归 lead / 机械类派出 → 助手在做 → 等回答 → 检查中 → 待审查 → 已验收或退回。工具只允许合法的转换:检查没过不能验收,问题没答不能验收。

## 10. 台账
- **保留,但改成自动记录。** mod 的 `turn.step` 事件每次请求都带回 lead 的真实用量(输入、输出、缓存读写),不用再让 lead 去读 Claude 应用的用量工具手动记。这是会话运行中的数据,不是去读 Claude 的记录文件。助手的用量照旧从 Codex 的事件里拿
- **放在 Fusion 栏里显示一行**:例如"本任务 lead 1.2M token · 助手 4.8M(缓存 96%)"
- **点"台账"按钮打开面板**:按任务列出 lead 和助手的用量、轮数、检查失败次数、换人信号,再加一张简单的图(Desktop 支持 SVG),代替帕累托查看器
- lead 工具调用次数可以继续算,但真实 token 比调用次数更准
